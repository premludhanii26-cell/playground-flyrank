# NOTES: Manual Accessible Components vs. shadcn/ui

After manually building the Modal, Tabs, and Disclosure components and strictly adhering to W3C ARIA practices, I reviewed the source code generated by `shadcn/ui` (which relies heavily on Radix UI primitives). 

Here are the concrete gaps where shadcn handles edge cases that my manual version missed:

### 1. Robust Focus Management & Portals (Dialog/Modal)
*   **The Gap:** In my manual `Modal`, I wrote a custom focus trap using `keydown` event listeners and queried focusable elements. While this traps focus, it fails if elements are injected dynamically. Furthermore, my modal is rendered strictly in the DOM hierarchy. 
*   **How shadcn handles it:** Shadcn uses Radix's `DialogPrimitive.Portal` to mount the modal directly to the `<body>` (avoiding CSS `z-index` and `overflow: hidden` clipping issues). Additionally, it uses a dedicated `FocusScope` primitive that handles edge cases like iframe focus, ensuring focus is reliably returned to the exact trigger element even if the DOM shifted.

### 2. Body Scroll Locking & Layout Shift (Dialog)
*   **The Gap:** When my manual modal opens, if the background page is long, the user can still scroll the background body with their mouse wheel. 
*   **How shadcn handles it:** Shadcn utilizes Radix's `RemoveScroll` utility, which automatically applies `overflow: hidden` to the body and adds `padding-right` to compensate for the disappearing scrollbar, preventing a jarring layout shift when the modal opens.

### 3. Roving Tabindex & RTL Support (Tabs)
*   **The Gap:** My manual `Tabs` component uses basic `ArrowRight` and `ArrowLeft` logic for keyboard navigation. 
*   **How shadcn handles it:** Shadcn accounts for horizontal/vertical orientations dynamically and automatically adjusts the arrow key logic. More importantly, it natively handles `dir="rtl"` (Right-to-Left) languages, flipping the arrow key logic automatically, which my manual version completely ignores.
